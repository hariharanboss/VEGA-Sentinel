# Dataset Methodology — VEGA Sentinel

> **Honesty first:** no measurement in this repository is fabricated. The
> dataset is small; historical labels include artificial/test entries;
> real-world accuracy is **not yet validated**.

## Collection protocol

- **Sampling interval:** 2500 ms (all sensors, common cadence — bounded by DHT22's ≥2 s requirement).
- **Firmware output:** `timestamp_ms,temp_c,humidity_pct,mq2_adc,flame_state,dht_ok`
- **PC logger enrichment** (`tools/data_logger/sentinel_logger.py` v0.4): adds `laptop_timestamp`, `label`, `experiment`, `phase`; validates every row (DHT range checks, flame ∈ {0,1}, MQ-2 ∈ 0–2047); rejects invalid rows to a separate file.
- **DHT failures:** rows with `dht_ok=0` are recorded (temp/hum = −999) but **excluded from training** — matching the firmware's discard policy.

### Labels

- `normal` — ordinary environmental behaviour.
- `warning` — mild deviation (used during some historical sessions).
- `critical` — abnormal/event condition (e.g., during a supervised flame trial).

### Phases

- `baseline` — pre-event.
- `event` — stimulus active.
- `recovery` — post-event return toward normal.

### Window labelling rule

A window is labelled **abnormal (1)** if it contains ≥1 `critical` sample;
otherwise **normal (0)**.

> ⚠️ **Label honesty:** some historical labels were set manually during
> early logger experiments and include artificial/test entries. Files listed
> as "not final training data" below are excluded from training claims.
> No fabricated measurements exist in this repository.

## Window generation

- **Window size:** 10 samples (~22.5 s at 2.5 s sampling).
- **Offline v3 dataset:** non-overlapping windows (stride 10) — 107 windows (100 normal / 7 abnormal).
- **Deployment:** stride 1 (true sliding window), regenerated per new valid sample.
- ⚠️ **Leakage caveat:** the historical CV randomly split windows; overlapping/adjacent windows from the same trial can appear in train and test. Use `ml/validation/validate_model.py` (leave-one-trial-out) for leakage-aware evaluation, and prefer trial-level splits in the upcoming retrain.

## Feature extraction (per window)

| # | Feature | Definition |
|---|---|---|
| 1 | humidity_mean | mean of humidity_pct |
| 2 | temp_mean | mean of temp_c |
| 3 | mq2_range | max−min of mq2_adc |
| 4 | mq2_delta | last−first mq2_adc |
| 5 | mq2_std | sample std (n−1) of mq2_adc |
| 6 | humidity_std | sample std (n−1) of humidity_pct |
| 7 | flame_fraction | fraction of samples with flame=1 |

(Additional analysis-only features are generated by
`ml/data_processing/generate_windows.py` but are not used by Model A.)

**Consistency requirement:** offline features must be computed identically
to the firmware (n−1 std, same order, same window semantics).

## Limitations

1. **Scale:** 107 windows (7 abnormal). Far too small for generalization claims.
2. **Abnormal diversity:** abnormal windows come from only 3 short flame-trial sessions; no gas/smoke-only or drift-failure events are represented.
3. **Environment specificity:** data reflects one room, one day (2026-09-11); sensor baselines (MQ-2 ~130–260 counts, humidity ~69–80 %, temp ~27.8–28.8 °C) are specific to that setting.
4. **Label reliability:** critical labels during flame trials mark operator-annotated event windows, not independently verified physical ground truth.
5. **No robust validation yet:** trial-level splits and false-positive-rate evaluation on fresh data are planned, not performed.
